# ArchMentor — приложение для изучения архитектуры от Junior до Lead

**Дата:** 2026-07-04
**Статус:** утверждён дизайн, готов к плану реализации

## 1. Цель и рамки

Клиентское SPA для изучения архитектуры ПО: **SOLID**, **23 GoF-паттерна**,
**архитектурные стили**, **trade-offs**. Обучение построено как траектория по
грейдам **Junior → Middle → Senior → Lead** со свободным доступом ко всем темам.

Ключевые механики обучения:
- **Флешкарты** с определениями (флип, интервальные повторения SM-2).
- **Квизы**, включая сигнатурный режим «**определи паттерн по коду**».
- **Прогресс** и статистика в localStorage.

Язык: **интерфейс и объяснения — русский**, **названия паттернов/терминов — английские**
(индустриальный стандарт). Примеры кода — TypeScript.

### Не входит (YAGNI на старте)
- Бэкенд, аккаунты, синхронизация между устройствами.
- Системный дизайн / распределённые системы / CAP (это отдельная будущая веха «Максимум»).
- Мультиязычность контента (только RU-объяснения + EN-термины).
- Редактор контента в UI (контент — это код).

## 2. Технологический стек (утверждён)

| Слой | Выбор |
|---|---|
| Сборка | Vite + React 18 + TypeScript (`strict: true`) |
| Роутинг | React Router v6 |
| Состояние | Zustand + `persist` (localStorage) |
| Стили | Tailwind CSS (тёмная тема — базовая) |
| Контент | Типизированные TS-модули + валидация **zod** на старте |
| Подсветка кода | `shiki` (предпочтительно) или `react-syntax-highlighter` как fallback |
| SRS | Собственный модуль SM-2 (чистые функции + unit-тесты) |
| Тесты | Vitest (+ Testing Library для ключевых компонентов) |

## 3. Структура модулей

Чистые границы: **контент ↔ доменная логика ↔ стор ↔ UI**. Каждый слой тестируется независимо.

```
src/
  app/          роутер, layout, провайдеры, тема, ErrorBoundary
  content/      типизированные данные: concepts/, questions/, schema (zod), index
  domain/
    srs/        SM-2: чистые функции + тесты
    quiz/       выбор вопросов, режимы, подсчёт результата
  store/        zustand-слайсы + persist + миграции версий
  features/     dashboard · learn · review · quiz · library · progress
  components/   переиспользуемый UI: Card, CodeBlock, ProgressBar, FlipCard, Badge…
  lib/          утилиты: даты, storage, type guards
  styles/       tailwind entry, глобальные стили
```

Роуты:
- `/` — Дашборд (текущий грейд, прогресс по уровням, «due на сегодня», streak, продолжить).
- `/learn/:conceptId?` — изучение флешкартами по теме/грейду.
- `/review` — SRS-повторение (только due-карточки).
- `/quiz` — квизы: выбор режима (по категории/грейду/микс) + режим «определи паттерн».
- `/library` — каталог концептов, фильтры (category/grade), поиск, страница концепта.
- `/progress` — статистика, mastery по темам, история.

## 4. Модель данных (замороженная схема — сердце проекта)

Единый тип `Concept` для принципов, паттернов и архстилей:

```ts
type Grade = 'junior' | 'middle' | 'senior' | 'lead';
type Category =
  | 'solid'        // 5 принципов
  | 'creational'   // порождающие GoF
  | 'structural'   // структурные GoF
  | 'behavioral'   // поведенческие GoF
  | 'architecture' // Layered, Hexagonal, Clean, MVC/MVVM, Event-driven, Microservices/Monolith
  | 'tradeoff';    // сквозные компромиссы

interface CodeSample {
  lang: 'typescript';
  code: string;
  highlightLines?: number[];
}

interface Concept {
  id: string;            // 'strategy', 'srp', 'hexagonal' (kebab/lower, уникален)
  name: string;          // EN: 'Strategy'
  aka?: string[];        // альтернативные названия
  category: Category;
  grade: Grade;          // рекомендуемый уровень
  tagline: string;       // RU, одна строка — суть
  definition: string;    // RU
  problem: string;       // RU: какую боль решает
  solution: string;      // RU: как решает
  codeExample: CodeSample;
  pros: string[];        // RU
  cons: string[];        // RU
  tradeoffs: string[];   // RU
  whenToUse: string[];   // RU
  whenNotToUse?: string[];// RU
  related: string[];     // id родственных/путаемых концептов
  tags?: string[];
}

type QuestionType = 'identify-pattern' | 'concept' | 'tradeoff' | 'code-smell';

interface Question {
  id: string;
  type: QuestionType;
  category: Category;
  grade: Grade;
  prompt: string;                 // RU
  code?: CodeSample;              // для identify-pattern / code-smell
  options: string[];             // варианты (EN-названия или RU-утверждения)
  correctIndex: number;          // индекс верного в options
  explanation: string;           // RU: почему верно И почему дистракторы — нет
  conceptId?: string;            // ссылка на связанный концепт
}
```

**Флешкарта** выводится из `Concept` детерминированно:
лицо = `name` + `tagline`; оборот = `definition` + `whenToUse`.
(Отдельный тип `Flashcard` не нужен — карточка = проекция концепта; SRS хранит состояние по `conceptId`.)

**Валидация:** при инициализации приложения весь контент прогоняется через zod-схемы.
Нарушения (дубли id, битые `related`/`conceptId`, `correctIndex` вне диапазона) → явная ошибка
в dev, безопасная деградация в prod. Битые данные не доходят до UI.

## 5. Сигнатурная фича — «Определи паттерн по коду»

Проектируется осознанно — это самая сложная часть контента:
- Код **идиоматичный** и имеет **ровно один защитимый ответ**.
- Дистракторы — **именно путаемые соседи**, а не случайные паттерны:
  - Strategy ↔ State
  - Factory Method ↔ Abstract Factory
  - Adapter ↔ Facade ↔ Proxy
  - Decorator ↔ Proxy
  - Observer ↔ Publish/Subscribe (Mediator)
  - Template Method ↔ Strategy
- `explanation` объясняет, почему верный вариант верный и почему **каждый** сосед — мимо.

Это требование фиксируется в промптах генерации контента (фаза 2), иначе получаются
тривиально угадываемые вопросы.

## 6. SRS-движок (SM-2)

Честная реализация алгоритма **SM-2** как набор чистых функций, покрытых unit-тестами.

```ts
interface SrsState {
  conceptId: string;
  ease: number;         // EF, старт 2.5, минимум 1.3
  interval: number;     // дни
  repetitions: number;  // число успешных подряд
  due: string;          // ISO-дата следующего показа
  lastReviewed?: string;
}

// quality 0..5. UI-кнопки → quality:
// Again = 2, Hard = 3, Good = 4, Easy = 5 (0/1 зарезервированы под «полный провал»)
function review(state: SrsState, quality: 0|1|2|3|4|5, today: string): SrsState;
```

Правила SM-2 (реализовать буквально):
- `quality < 3` → `repetitions = 0`, `interval = 1` (карточка возвращается).
- `quality >= 3` → `repetitions += 1`; интервал: 1 → 6 → `round(prevInterval * ease)`.
- Обновление ease: `ease += 0.1 - (5 - q) * (0.08 + (5 - q) * 0.02)`, но не ниже 1.3.
- `due = today + interval` дней.

**Детерминизм и тестируемость:** «сегодня» всегда передаётся аргументом (никаких `Date.now()`
внутри чистых функций). Тесты покрывают: первый показ, провал-сброс, рост интервалов,
пол ease 1.3, границы quality.

## 7. Прогресс (Zustand + persist)

Слайсы стора:
- `srs`: `Record<conceptId, SrsState>`.
- `quizResults`: попытки по вопросам (verdict, timestamp) + агрегаты по category/grade.
- `conceptProgress`: `Record<conceptId, { seen: boolean; mastered: boolean }>`.
- `streak`: `{ current, longest, lastActiveDate }`.
- `settings`: `{ theme, gradeFilter, categoryFilter }`.

Persist:
- Ключ `archmentor:v1`; поле `version` для миграций.
- При несовместимой смене схемы контента — миграция или безопасный сброс прогресс-слайсов
  (контент-слайсы не персистятся — контент всегда из кода).

Определение грейда пользователя (для траектории): грейд «пройден», когда mastered ≥ X%
концептов этого грейда И средняя правильность квизов грейда ≥ Y%. Пороги (X, Y) фиксируются
в фазе 1 на seed-контенте.

## 8. Экраны (UX)

- **Дашборд:** текущий грейд + прогресс-бар по 4 уровням; блок «due сегодня» с CTA
  «Повторить»; streak; «продолжить обучение» (следующий незакрытый концепт).
- **Learn:** флип-карточки по выбранной теме/грейду; свайп/кнопки «дальше»; переход к
  полной странице концепта.
- **Review:** только due-карточки; оценка Again/Hard/Good/Easy; прогресс сессии.
- **Quiz:** выбор режима (микс / по категории / по грейду / «определи паттерн»); показ кода
  с подсветкой; после ответа — мгновенный разбор (`explanation`); итог сессии.
- **Library:** сетка/список концептов с фильтрами и поиском; страница концепта
  (definition, problem, solution, code, pros/cons, trade-offs, when-to-use, related).
- **Progress:** mastery по темам и грейдам, точность квизов, календарь/streak, история.

Пустые состояния, загрузка и ошибки (ErrorBoundary) проектируются явно.

## 9. Фазирование реализации

**Фаза 1 — Вертикальный срез (доказать цикл, заморозить схему).**
Каркас Vite+React+TS, Tailwind, роутер, стор (persist), **SRS с тестами**, zod-схемы,
и **все экраны**, работающие на *seed*-контенте:
- SOLID: все 5 принципов.
- Паттерны: Strategy, Observer, Factory Method (+ их «соседи» как дистракторы).
- ~10–12 вопросов, включая ≥4 «определи паттерн».
Критерий готовности фазы: полный цикл (учить → повторять по SRS → квиз → прогресс) работает,
схема заморожена.

**Фаза 2 — Массовая генерация контента (Workflow fan-out, ultracode).**
По замороженной схеме: один агент на концепт → структурный вывод → **adversarial-проверка**
корректности определения и кода + однозначности ответа квиза (дистракторы = соседи).
Все данные валидируются zod. Полный набор: 5 SOLID + 23 GoF + архстили + trade-offs, с квизами.

**Фаза 3 — Полировка.**
Тёмная тема, доступность (a11y, клавиатура, фокус), пустые/edge-состояния, адаптив,
финальный прогон и сборка.

## 10. Планка корректности (жёсткое требование)

Учебное приложение с неверным определением или мислейбл-паттерном хуже, чем его отсутствие.
- Каждое определение сверяется с каноном: **GoF** (Gamma et al.) для паттернов,
  **Robert C. Martin** для SOLID/Clean.
- Каждый код-сниппет — идиоматичный TS, компилируемый по смыслу, демонстрирует **ровно один** паттерн.
- Каждый «identify-pattern» имеет **ровно один защитимый ответ**; дистракторы — путаемые соседи.
- Гарантируется adversarial-проходом на фазе 2 + zod-валидацией целостности.

## 11. Тестирование

- **domain/srs:** unit-тесты SM-2 (см. §6).
- **domain/quiz:** выбор/подсчёт, отсутствие повторов в сессии, корректность вердиктов.
- **content:** zod-валидация всего датасета (uniqueness id, целостность `related`/`conceptId`,
  `correctIndex` в диапазоне, непустые обязательные поля).
- **store:** сериализация/десериализация, миграция версий.
- Ключевые UI-компоненты (FlipCard, Quiz flow) — Testing Library smoke-тесты.

## 12. Риски и решения

| Риск | Решение |
|---|---|
| Неверный/поверхностный контент | Adversarial-проверка (фаза 2), сверка с каноном, zod |
| Схема «плывёт» после массовой генерации | Заморозка на вертикальном срезе (фаза 1) до генерации |
| Тривиальные вопросы «определи паттерн» | Обязательные дистракторы-соседи, зафиксировано в §5 |
| Кривая математика интервалов | Буквальная SM-2, чистые функции, unit-тесты |
| Раздувание localStorage / несовместимость | Версионирование + миграции, контент не персистится |
