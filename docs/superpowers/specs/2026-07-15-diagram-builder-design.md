# Diagram Builder — «Собери архитектуру»

**Дата:** 2026-07-15
**Статус:** дизайн утверждён, готов к плану

## Цель

Дать пользователю **активный** режим обучения: вместо узнавания (флеш-карточки) или
выбора ответа (quiz) он сам **строит** архитектуру под задачу и получает разбор. Это
закрывает главный пробел приложения — применение теории к реальной задаче system design и
визуальное мышление.

## Область (scope первой версии)

- **3–4 сценария-задачи:** URL shortener, лента новостей, rate limiter, чат.
- **Уровень проверки B — граф + связи:** проверяем и наличие блоков, и правильность
  соединений между ними.
- **Цикл:** собрать схему целиком → «Проверить» → отчёт (✓/⚠/✗ построчно) + эталонная схема.
- **Полная интеграция:** сайдбар + Dashboard-карточка + ⌘K + прогресс на экране Progress.

Вне области: LLM-оценка свободных схем (нет бэкенда, ломает офлайн-детерминизм),
пользовательские сценарии, живая пошаговая обратная связь.

## Ключевое архитектурное решение

Два выбора — **React Flow** (канва) и **клавиатурный режим для сохранения AA** — вместе
означают, что **списочный конструктор является обязательным ядром**, а не дополнением:
добавить блок / соединить X→Y / удалить / сабмит — это вся механика, и клавиатурному
пользователю нужно всё это целиком.

Следствие: React Flow — это **надстройка-адаптер** (view + input) поверх той же модели
`{nodes, edges}`, что и списочный конструктор. Фича полностью работоспособна без React Flow;
библиотека (~50–90 КБ gzip) оправдана **только полировкой UX мышью**, и это осознанный
компромисс, а не скрытая стоимость.

**Порядок реализации (обязательный):** модель → домен валидации → списочный конструктор
(AA-ядро) → канва React Flow. Так a11y не «прикручивается последней» и AA-обязательство не
теряется.

## Архитектура по единицам

### 1. Домен — `src/domain/diagram/`

Чистый, framework-agnostic, полностью юнит-тестируемый (как `srs`, `compare`, `daily`).

**Модель графа:**

```ts
interface DiagramNode { id: string; type: ComponentType }
interface DiagramEdge { from: string; to: string }
interface Diagram { nodes: DiagramNode[]; edges: DiagramEdge[] }
```

Форма совпадает с тем, что отдаёт/принимает React Flow (после тривиального маппинга), так
что канва остаётся тонким адаптером.

**Валидация — по ограничениям (constraints), НЕ по эталону.** System design допускает
множество верных схем; сверка «точь-в-точь с образцом» забракует правильные альтернативы и
убьёт образовательную ценность. Правило сценария — набор constraint'ов:

- `requiredNodes` — типы блоков, которые обязаны присутствовать → ✓/✗
- `forbiddenNodes` / `discouraged` — лишние/нежелательные блоки → ⚠/✗
- `requiredEdges` / отношения — например «cache расположен между app и db» → ✓/⚠

```ts
type Status = 'ok' | 'warn' | 'fail'
interface CheckResult { status: Status; messageKey: string; params?: Record<string, string> }
function validate(diagram: Diagram, scenario: Scenario): CheckResult[]
```

Каждый constraint даёт **свою** строку фидбэка.

**Инвариант проектирования правил:** валидная, но отличная от эталона схема ДОЛЖНА
проходить. При написании каждого набора правил проверяем это явно; если валидная
альтернатива не проходит — правило слишком жёсткое и переписывается на более общее
ограничение.

Эталонная схема хранится в сценарии и показывается **после** сабмита как *иллюстрация
одного из решений*, а не как ключ проверки.

### 2. Контент — `src/content/diagram.ts`

Zod-валидируется, все тексты `{ ru, en }` (как весь контент).

- **Общий словарь палитры** `ComponentType`: Client, LoadBalancer, ApiServer, Cache (Redis),
  SqlDb, NoSqlDb, MessageQueue, CDN, ObjectStore, RateLimiter (и по мере надобности). Один
  список, переиспользуется всеми сценариями; у каждого типа — локализованное имя и краткое
  описание.
- **Сценарий:** id, заголовок, описание задачи (`{ru,en}`), требования/нагрузка,
  доступная палитра (подмножество типов), набор constraint'ов, эталонная схема `Diagram`.

**Отдельная единица внимания — составные строки фидбэка.** Билингвальные сообщения по
каждому типу constraint'а (с подстановкой имён блоков) — нетривиальная часть локализации.
Проектируется осознанно как отдельный набор ключей в `messages`, а не дописывается в конце.

### 3. Store — `src/store/useStore.ts`

- Новый персист-слайс:

  ```ts
  interface DiagramState { completed: Record<string, { at: string; passed: boolean }> }
  ```

- Экшен `completeScenario(id, passed, today)` → пишет результат + `bumpStreak(...)` (как все
  режимы: пройденный сценарий = активность).
- **Миграция version 3 → 4:** добавить `diagram` в `initialData()`, `PersistedState`,
  `partialize`; расширить диапазон в `migrate` (тривиальный backfill через `merge`, как
  v2→v3). Существующий прогресс сохраняется.
- Селекторы: `isScenarioDone(state, id)`, `selectDiagramProgress(state, scenarios)`
  (пройдено / всего / pct) для экрана Progress.

### 4. Фича-экран — `src/features/diagram/`

- Роуты `diagram` и `diagram/:scenarioId?` в `src/app/App.tsx` (lazy, как все режимы).
- **Списочный конструктор (AA-ядро):**
  - панель «палитра» — кнопки «добавить блок»;
  - список добавленных нод с возможностью удаления;
  - соединения: «[from ▾] → [to ▾]» + добавить/удалить связь;
  - кнопка «Проверить» → отчёт `CheckResult[]` построчно (✓/⚠/✗) + эталон.
  - Полностью управляется с клавиатуры, семантические элементы, соответствует AA.
- **Канва (React Flow):** тот же экран, переключатель вида «список / канва». Кастомные ноды —
  React-компоненты, наследуют тему (CSS-переменные) и i18n. Drag-and-drop, соединение через
  handles, pan/zoom. Пишет в ту же модель `Diagram`. Изолирован как input-адаптер; отсутствие
  React Flow не ломает списочный режим.
- **Интеграция (полная):**
  - пункт в `NAV` (`src/app/Layout.tsx`) + ветка в `titleKeyFor`;
  - карточка на Dashboard;
  - вход в `CommandPalette`;
  - блок прогресса на экране Progress через `selectDiagramProgress`.

### 5. Тесты

- **Домен** `src/domain/diagram/validate.test.ts` — полноценно: каждый тип constraint'а,
  и **обязательный кейс «валидная альтернатива, отличная от эталона, проходит»**.
- **Контент** — Zod + кросс-ссылки: типы нод в constraint'ах и эталонах существуют в палитре
  (по образцу `schema.test.ts`).
- **Store** — миграция v3→v4, `completeScenario`, влияние на стрик.
- **Экран** — смоук списочного конструктора: добавить блоки → соединить → сабмит → отчёт.
  Канву React Flow в jsdom не тестируем (нужны размеры/ResizeObserver) — соответствует
  текущему подходу «вся логика в домене».

## Рассмотренные и отклонённые варианты

- **Уровень валидации:** A (только наличие блоков) — слишком бедный фидбэк; **B
  (граф + связи) — выбрано**; C (свободная схема + LLM) — требует бэкенда, ломает
  офлайн-детерминизм проекта.
- **Канва:** собственная реализация со стрелками — недели работы и хуже UX; **React Flow —
  выбрано** как тонкий view/input-адаптер.
- **a11y:** исключение канвы из AA-политики — отклонено (нарушает единую политику);
  **альтернативный клавиатурный/списочный режим — выбрано** (и оказался обязательным ядром).

## Критерии готовности

- 3–4 сценария играбельны в обоих режимах (список и канва), билингвально, в тёмной/светлой теме.
- Валидация по constraint'ам пропускает валидные альтернативы; отчёт построчный с ✓/⚠/✗.
- Списочный режим полностью доступен с клавиатуры (AA сохранён).
- Прогресс персистится (v4), виден на Dashboard и Progress, влияет на стрик.
- Все существующие тесты зелёные + новые для домена/контента/store/экрана.
