# Diagram Builder: сценарии + уровни сложности — дизайн

**Дата:** 2026-07-15
**Статус:** дизайн утверждён, готов к плану
**Расширяет:** `docs/superpowers/specs/2026-07-15-diagram-builder-design.md` (фича `/diagram`, на master)

## Цель

Углубить контент режима `/diagram`: довести число сценариев с 3 до **8**, распределить их
по грейдам **junior → middle → senior → lead** (по 2 на грейд) и сгруппировать пикер по
грейдам с бейджами. Даёт ощущение «пути по сложности» и больше материала для практики,
переиспользуя уже готовый движок валидации.

## Область (scope)

- Добавить поле `grade` в `Scenario` и проставить его всем сценариям.
- 5 новых сценариев + грейды на 3 существующих = 8 всего (2/2/2/2).
- Пикер (`ScenarioPicker`) группируется по грейдам с заголовками и бейджами.
- Смягчить `cdn` в сценарии `news-feed` с hard-required до warn (отложенный фикс из
  прошлой сборки — валидный дизайн без CDN сейчас ошибочно падает; делаем заодно, раз
  трогаем контент).

Вне области: прогрессивный гейтинг (лок грейдов), пер-грейдовый прогресс на
Dashboard/Progress, изменения движка валидации/канвы/стора, новые роуты/экраны.

## Ключевые решения

- **Грейд — чисто метка сложности.** Механически ни на что не влияет: `validate`, `isPassed`,
  edit-хелперы, канва, стор — без изменений. Сложность выражается естественно через контент
  (у старших грейдов больше компонентов и ограничений). Это гайдлайн авторинга, не код.
- **Мягкий гейтинг.** Все сценарии видны и кликабельны; грейды только группируют и
  подписывают (как Course/Library). Никакого нового состояния блокировки.
- **Переиспользование существующей грейд-инфраструктуры:** `GradeSchema` (`src/content/schema.ts`),
  `GRADE_ORDER` и `GRADE_LABEL` (`src/lib/labels.ts`), и тот же стиль грейд-бейджа, что в
  Library/Compare.

## Архитектура по единицам

### 1. Схема контента — `src/content/diagram.ts`

- В `ScenarioSchema` добавить `grade: GradeSchema` (импорт из `./schema`). Тип `Scenario`
  (через `z.infer`) получает поле автоматически.
- `validateScenarios` дополнительно проверяет: `grade` валиден (гарантируется Zod-энумом) —
  явных новых кросс-проверок не требуется сверх текущих (типы ∈ палитра, эталонные рёбра
  ссылаются на известные id, уникальность id).

### 2. Контент — 8 сценариев (2/2/2/2)

Существующим проставить грейд, добавить 5 новых. Каждый сценарий: `id`, `grade`,
`title`/`brief` (`{ru,en}`), `palette` (подмножество типов), `constraints`, `reference`.

- **junior:**
  - `blog-api` *(new)* — простой CRUD-бэкенд: client → LB → api → SQL/NoSQL. База механики.
  - `url-shortener` *(есть)* — client → api → cache → datastore; read-heavy, кэш.
- **middle:**
  - `rate-limiter` *(есть)* — client → rate-limiter → api → cache.
  - `file-upload` *(new)* — загрузка файлов/картинок: client → api → object-store + CDN на
    отдачу.
- **senior:**
  - `news-feed` *(есть, правится)* — лента с медиа: api → cache + datastore, CDN.
  - `chat` *(new)* — мессенджинг: client → api/gateway → message-queue → datastore,
    presence-кэш.
- **lead:**
  - `notifications` *(new)* — fan-out: api → message-queue → воркеры → провайдеры (мульти-
    канал).
  - `video-streaming` *(new)* — аплоад → object-store → очередь транскодинга → CDN;
    глобальная отдача.

**Инвариант рул-дизайна (обязателен для каждого сценария):** эталон проходит собственные
ограничения; валидная альтернатива, отличная от эталона, тоже способна пройти; только
отсутствие required-node / присутствие hard-forbidden дают `fail`, кривая разводка = `warn`.
Проверяется тестом (см. §5).

**Новые типы компонентов:** если сценарии старших грейдов требуют компонент, которого нет в
текущих 10 (кандидаты: `worker`, `api-gateway`), добавить его в `COMPONENT_TYPES`
(`src/domain/diagram/types.ts`) и в `componentNames` (`src/content/diagram.ts`, `{ru,en}`).
Если можно выразить существующими 10 типами — не расширять палитру (YAGNI). Решается при
авторинге каждого сценария.

### 3. Фикс `news-feed`

Заменить ограничение `{ kind: 'required-node', node: 'cdn' }` на более мягкое: либо
`{ kind: 'forbidden-node' ... }` не подходит — нужно поощрять CDN, но не валить без него.
Правильно: убрать `cdn` из hard-required и выразить как `required-edge` (например
`client → cdn` или `api-server → cdn`), который в текущем движке даёт `warn` при отсутствии.
Итог: дизайн без CDN получает предупреждение, но проходит (`isPassed`), что соответствует
инварианту. Обновить эталон при необходимости, чтобы он по-прежнему проходил.

### 4. UI пикера — `src/features/diagram/Diagram.tsx` (`ScenarioPicker`)

- Сейчас — плоский список. Переделать в **секции по грейдам** в порядке `GRADE_ORDER`:
  заголовок грейда (через `GRADE_LABEL`, локализованный) + карточки сценариев этого грейда.
- На каждой карточке — грейд-бейдж в стиле Library/Compare и существующий бейдж прохождения
  (✓ при `completed[id]?.passed` + `sr-only` текст `diagram.done`).
- Всё кликабельно (мягкий гейтинг). Роуты, `ScenarioBuilder`, канва, отчёт — без изменений.
- Заголовки грейдов: `GRADE_LABEL` — это `Record<Grade, string>` с языко-нейтральными
  именами (`Junior`/`Middle`/`Senior`/`Lead`), используемыми как есть в обоих языках (так же,
  как в Course/Library/Compare). Новых i18n-ключей для заголовков грейдов не нужно. Если
  понадобится подпись-обёртка (напр. «Уровень: {grade}»), добавить один ru/en-ключ.

### 5. Прогресс

Без изменений: `selectDiagramProgress` и счётчики Dashboard/Progress остаются суммарными
(«пройдено N/8»). Пер-грейдовая статистика — вне области (YAGNI).

### 6. Тесты

- **Контент** (`src/content/diagram.test.ts`, расширить):
  - у каждого сценария валидный `grade` (Zod-парс уже ловит, плюс явная проверка присутствия);
  - **каждый эталон проходит свои ограничения** (тест уже есть — применится ко всем 8);
  - `scenarios.length >= 8` и покрыты все 4 грейда (по ≥1 сценарию на грейд, фактически 2);
  - кросс-рефы (типы constraint'ов и эталонов ∈ палитра) — существующий `validateScenarios`
    применится к новым;
  - если добавлены новые типы компонентов — у них есть `componentNames` (гард как для
    остальных типов, тест «каждый ComponentType имеет ru/en имя»);
  - `news-feed`: валидный дизайн без CDN проходит (`isPassed` == true) — закрепляет фикс §3.
- **Экран** (`src/features/diagram/Diagram.test.tsx`, дополнить смоук):
  - пикер рендерит секции по грейдам (заголовки видны) и грейд-бейджи присутствуют;
  - существующий флоу сборки/сабмита не сломан.

## Рассмотрено и отклонено

- **Прогрессивный гейтинг** (лок грейдов до прохождения предыдущего) — фрустрирует, требует
  нового состояния и логики разблокировки. Отклонено.
- **Только фильтр по грейду** (как `gradeFilter` в Квизе) — не даёт визуальной структуры
  «пути». Отклонено в пользу группировки.
- **Пер-грейдовый прогресс на Dashboard/Progress** — YAGNI; отдельная итерация при желании.

## Критерии готовности

- 8 сценариев (2/2/2/2), у каждого валидный `grade`; играбельны в обоих режимах,
  билингвально, в тёмной/светлой теме.
- Пикер сгруппирован по грейдам с бейджами; всё кликабельно; бейдж прохождения корректен.
- `news-feed` без CDN проходит (с warn); все эталоны проходят свои ограничения.
- Все существующие тесты зелёные + новые контент/экран-тесты; tsc и build чистые.
